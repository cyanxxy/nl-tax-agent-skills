# Annual Return Workpack — Output Contract

This document defines the required structure, validation rules, and quality
constraints for the 2025 annual income-tax workpack. Every workpack generated by
the `nl-tax-annual-return` skill must satisfy all rules in this contract. The
skill's `SKILL.md` is procedure; this file is the binding spec for the
workpack's content. The template is `templates/annual-workpack.md`.

## Output location and consent

- By default nothing is written. The workpack is shown in the conversation as
  Markdown, or on a host surface that creates no file. Presentation never
  writes: creating a downloadable file counts as saving. In chat, render only
  filled sections, with no template fill notes, no bracketed instructions, and
  no Appendix A or Appendix B YAML (the field map appears as its summary
  table).
- The only file this skill may write is `workspace/nl-tax-annual-2025-workpack.md`,
  relative to the task's working folder, and only while save consent is active
  in this conversation (a fresh yes, a found file the taxpayer confirmed
  resuming, or an attached copy the taxpayer agreed to keep saving). Appendix A
  `save_consent` records that decision; it never authorizes a write. Update
  that file in place; never create a copy, a `-v2` or dated variant, or a
  second `workspace/` tree. A file at that path that the taxpayer did not
  resume is replaced only after the replace-or-keep question in the runtime
  contract, never merged into.
- Inside that file, this skill writes every section except `Field map summary`
  and Appendix B (written by `nl-tax-field-mapper`), the mapper's own gap rows
  in `Open questions` and `Missing information` with their Q-IDs in Appendix A
  (also written by `nl-tax-field-mapper`), and `Manual-entry checklist`
  (written by `nl-tax-submit-companion`). The first save writes everything
  established so far from the facts and provenance recorded in the
  conversation. An unsaved field map is not state: for that save, and at every
  regeneration, `nl-tax-field-mapper` rebuilds the map from the recorded facts
  and re-runs every FM-* check before writing `Field map summary` and Appendix
  B; a checklist already shown is carried over only when each of its values
  matches the rebuilt map, otherwise with the stale line below. After the
  first save each writer keeps only its own sections current.
- Stale outputs: when a sourced fact changes after generation,
  `generation_confirmed` returns to `false`, and this skill adds the line
  `STALE — predates the change to <fact> (<YYYY-MM-DD>); regenerate before
  use.` at the top of `Field map summary`, of Appendix B (above the `yaml`
  block), and of a requested `Manual-entry checklist`, and shows it in the
  conversation. That line is the only edit this skill makes in those sections.
  A stale marker is valid only while `generation_confirmed` is `false`;
  regeneration re-runs the mapper, which replaces the stale summary and
  Appendix B.
- Once mapping has run, `Field map summary` is the checked surface, in the
  saved file and in the conversation: every `manual_entry` field in Appendix B
  appears in it with the same value, and every `missing_fields` entry appears
  as a `MISSING - enter manually` row with its Q-ID.
- This skill never writes the provisional workpack or any other file, and never
  copies, moves, renames, or rewrites the taxpayer's documents.
- When consent is active and the host has no writable working folder, deliver
  the same workpack as a downloadable file or document through the host's
  normal output mechanism. When the working folder may not outlast the session,
  save there and also deliver a download at pauses and at generation. A
  download at generation is produced after mapping, so it includes the map.

A saved workpack exists before generation: it follows the same structure, and a
tax section the conversation has not reached yet holds the single line
`Not yet reviewed.` The self-check below applies at generation.

## Required sections

Every workpack MUST contain ALL of the following sections, in order. If a section is not applicable, the section must still be present with an explicit "not applicable" line — it must not be omitted.

1. **Title and STATUS banner** — see Status banner below, followed by the provenance convention
2. **How to use this file** — three lines: it is the taxpayer's own working file; keep it in the working folder or attach it to continue later; filing is always manual in Mijn Belastingdienst
3. **Contents**
4. **Scope** — tax year, workflow, taxpayer label (no name, BSN, or IBAN required), partner status, timestamp
5. **Unsupported-case checks** — checklist confirming the case is within scope
6. **Taxpayer profile summary** — the screened facts, one keyed row each with provenance: residency, taxpayer type, AOW status for 2025 (three-state value, transition month, single-person AOW entitlement), fiscal partner and partner AOW status, household composition (children at home, children's dates of birth, single-parent status), Box 2 screening, and business screening. No BSN, IBAN, or names
7. **Documents and sources** — one row per document or chat value used: `ev_NNN | document as named by the user | type | tax year | owner | location (page/section) | values taken | status (extracted / needs review)`. A chat value's row is named `chat YYYY-MM-DD` with type `user_chat`. No file hashes, no full BSN, IBAN, policy, contract, or aanslag number, and no copied content beyond the short quote needed for provenance
8. **Sources used** — the `source_id`s from `../nl-tax-shared-resources/source-register.yaml` actually consulted for the annual workflow, one per line, identical to Appendix A `sources_loaded`
9. **Filing status and late-filing exposure** — one of the four filing-route
   labels, timing facts, route-specific potential penalty, and belastingrente
   review when applicable
10. **Income notes** — all box 1 income categories (employment, pension, benefits, other)
11. **Winst uit onderneming notes** — the ordered profit chain from saldo fiscale winstberekening to belastbare winst uit onderneming with its derivation lines and provenance, the vermogensvergelijking self-check, the bijdrage Zvw consequence, the lijfrente and arbeidsinkomen bases, open questions, and manual-review routing
12. **Own-home notes** — WOZ, mortgage interest, eigenwoningforfait, tariefsaanpassing, Hillenregeling, plus verkoopregeling / aankoopregeling when applicable
13. **Box 2 notes** — substantial-interest status, regular benefits, disposal benefits, dividend withholding tax credit, loss setoff, partner allocation, manual-review triggers
14. **Box 3 notes** — assets, debts, fictitious return, actual return data, comparison, partner allocation
15. **Deductions notes** — alimentatie, zorgkosten, giften, lijfrentepremie, other
16. **Credits screening** — IACK, ouderenkorting, alleenstaande-ouderenkorting, jonggehandicaptenkorting triggers based on household composition
17. **Fiscal partner notes** — partner status, allocation options, review points
18. **Open questions** — every unanswered or deferred question: stable Q-ID, section key, question, blocking yes/no, ordered by impact. The field mapper adds its own rows for mapping gaps, continuing the Q001 numbering
19. **Missing information** — every `?` row as an M-ID with priority (critical / important / nice-to-have), the workpack row, the linked Q-ID, and how to resolve it. The field mapper adds its own rows for missing mapped values, continuing the M001 numbering
20. **Assumptions** — A-IDs, only assumptions the taxpayer explicitly accepted
21. **User-stated values index** — cross-index of every `U:` chat value so the user can spot-check what was recorded from chat
22. **Field map summary** — human-readable table of the Appendix B field map, written by the field mapper; `not yet mapped` until then
23. **Manual-entry checklist** — written by the submit companion only when the taxpayer asks for it; `not requested` until then
24. **Human review checklist** — items requiring human verification before filing, including every `U:` chat-only value
25. **Not submission advice** — mandatory disclaimer section
26. **Appendix A — Resume record** — one fenced `yaml` block (see Resume record)
27. **Appendix B — Field map** — one fenced `yaml` block holding the canonical annual field map, or the literal line `not yet mapped`

### Own-home calculation and review boundary

The own-home section must itemize mortgage interest, qualifying financing costs, and periodic erfpacht, opstal, or beklemming. Their sum is `total_deductible_own_home_costs`, and Hillen uses that total rather than mortgage interest alone.

Total deductible own-home costs include mortgage interest, qualifying financing costs, and periodic erfpacht, opstal, or beklemming.

`box1_own_home_balance = eigenwoningforfait - total_deductible_own_home_costs - hillen_deduction`

Tariefsaanpassing is separate from box1_own_home_balance. Show it in a separate review table as a tax-benefit adjustment and never add it to taxable Box 1 income. Optional helper fields are review inputs only: the agent verifies their evidence and keeps unresolved qualification or amount questions visible as manual review.

One ordinary main residence may receive a review estimate. Two homes, sale/purchase overlap, temporary double-home deductions, divorce use, and other complex cases must collect facts and route to manual review.

## Source attribution rules

### Amounts must have a source

Every monetary amount in the workpack MUST be attributed to one of:
- An `evidence_id` that exists as a row in Documents and sources (e.g., `F:ev_003`)
- An `assumption_id` listed in Assumptions when the amount is estimated or assumed (e.g., `A:A003`)
- A `quote` plus `stated_at` for `user_chat` values (e.g., `U:"my loon was 48,250" (2026-09-20)`)
- A `C:` derivation from rows that are themselves sourced

Amounts without source attribution are not permitted. If a figure cannot be sourced, it must be marked as an assumption with an explicit `assumption_id` or flagged with `Src: ?` and listed in Missing information.

When a document and a chat value, or two documents, disagree, do not choose
silently: mark the Documents and sources row `needs review`, describe the
conflict, and ask the taxpayer which value controls.

### Assumptions must be listed

Every assumption used in the workpack MUST appear in the Assumptions section with:
- A unique `assumption_id` (format: `A001`, `A002`, etc.)
- A description of what was assumed
- The taxpayer's explicit acceptance, with `U:` provenance
- The impact on the return if the assumption is incorrect
- A recommendation for how to resolve the assumption (e.g., "provide jaaropgaaf from employer X")

### Sources used must match the resume record

The Sources used section MUST list exactly the `source_id`s in Appendix A
`sources_loaded`: the reviewed sources actually consulted for this annual
workflow. Do not pad the list with sources that were not consulted, do not omit
consulted annual sources, and do not include provisional IDs. The list is
canonical, not aspirational.

## Filing status and late-filing exposure

The "Filing status and late-filing exposure" section MUST appear in every
workpack. First record exactly one evidence-backed route label:

- `invited`: use the deadline on the aangiftebrief. If late, present EUR 469
  first / EUR 6,709 repeated maximum only as potential exposure and record the
  herinnering, aanmaning, and **10 werkdagen** (10-workday) response-period facts.
- `no_letter_but_mandatory`: record which test applies—EUR 58 or more to pay, or
  entitlement to an income-dependent scheme with relevant assets above EUR
  37,395 (EUR 74,790 with a fiscal partner)—and the 14 July 2026 guardrail. If
  late, ask whether and when an aangifte was requested and present the separate
  EUR 3,354 failure-to-request amount, 6-month request period, and 2-week grace
  only as potential official exposure. Do not apply the invited-return
  reminder/aanmaning narrative to this route.
- `refund_claim_only`: record EUR 19 or more back and that neither mandatory
  no-letter test applies. Describe submission as a refund claim, not a mandatory
  invitation-based filing.
- `filing_obligation_unresolved`: state which official calculation or
  scheme/assets facts remain open. Do not invent a deadline or classify the
  taxpayer as late.

For `invited`, also record any granted uitsteldatum. "On time" means no
late-filing **penalty** exposure; it must not promise zero belastingrente.
Belastingrente can apply when the return was received on or after 1 May or when
the Belastingdienst deviates from the return, even if it was filed before
1 May. Quote applicable facts from `late-filing.md` without computing a final
amount.

Do not present the section as legal advice. The Belastingdienst determines
whether the relevant conditions are met and sets any actual boete and rente.

## Winst uit onderneming requirements

### The business section

The Winst uit onderneming section MUST be present.

**When it does not apply** (the taxpayer has no onderneming), emit exactly:

```
Not applicable — no winst uit onderneming reported.
business.has_onderneming: no
```

Do not enumerate the other fields. The single `business.has_onderneming: no` line is the canonical hook for the field map.

**When it applies**, the section carries a derived result, not an evidence pile.
Record the income-category screen first, require finalized 2025
profit-and-loss and balance evidence, then walk the ordered profit chain and
print every line with its inputs, its derivation and its provenance.

### The ordered profit chain

`../nl-tax-shared-resources/knowledge/years/2025/entrepreneur/winstberekening-2025.md` is canonical
for the order of the chain and for the component notes each amount comes from.
Read every rate, percentage, cap and threshold from those notes; this contract
deliberately restates none of them. Run the lines in this order and
do not relax the two order rules -- investeringsaftrek is subtracted before
ondernemersaftrek, and the MKB-winstvrijstelling base is the amount after both:

1. **Winst uit onderneming** -- the saldo fiscale winstberekening after the
   fiscal corrections (`winst-en-kosten.md`, `vervoer-2025.md`,
   `afschrijving-en-bedrijfsmiddelen-2025.md`,
   `aanloopfase-en-starters-2025.md`).
2. **Minus investeringsaftrek**, plus any desinvesteringsbijtelling
   (`investeringsaftrek.md`).
3. **Minus ondernemersaftrek**, subject to the winst cap and the starter
   exception to it (`ondernemersaftrek.md`,
   `partner-en-meewerken-2025.md`). Where the cap bites, state the resulting
   niet-gerealiseerde zelfstandigenaftrek, that the Belastingdienst fixes it by
   beschikking, and that it is not carried forward automatically
   (`verlies-en-verrekening-2025.md`).
4. **Minus the MKB-winstvrijstelling**, whose base is the amount after both of
   the previous steps (`mkb-winstvrijstelling.md`).
5. **Belastbare winst uit onderneming** -- the result of step 4. This amount IS
   a component of the box 1 income total in the Income notes section.
6. **Tariefsaanpassing**, presented as a separate belastingvermeerdering the
   aangifte computes on the grondslagverminderende posten. Never add it to
   taxable box 1 income and never present an agent-computed correction as the
   amount that will be assessed.

Every line needs its own amount, a named derivation, and an `evidence_id`,
`assumption_id`, or `quote` plus `stated_at`. A missing input is an open
question and a `?` row; it is never a zero, a prior-year figure, or an estimate
the agent supplies.

Three downstream bases are read off **different lines** of that same chain, and
the section MUST label each with the line it comes from:

- bijdrage-inkomen Zvw -- from the belastbare winst uit onderneming (step 5);
- lijfrente premiegrondslag -- the winst before ondernemersaftrek of the
  preceding calendar year, asked separately and not read off this year's step 2;
- arbeidsinkomen for the arbeidskorting -- from that same step 2 line.

Never reuse one of those amounts for another.

### Computed by the aangifte, not typed by the taxpayer

`../nl-tax-shared-resources/knowledge/years/2025/entrepreneur/zakelijke-schema-2025.md` is canonical
for the split. The taxpayer types the winst-en-verliesrekening rubrieken, the two
balans columns, the priveonttrekkingen en -stortingen, and the yes/no
eligibility answers. The **aangifte computes** the ondernemersaftrek components,
the total ondernemersaftrek, the kleinschaligheidsinvesteringsaftrek, the
MKB-winstvrijstelling and the belastbare winst from those figures and answers.

The computed amounts therefore belong in the workpack narrative, as expectations
the taxpayer checks against the screen. The annual field map MUST NOT contain
`onderneming.belastbare_winst`, `onderneming.zelfstandigenaftrek`,
`onderneming.startersaftrek`, `onderneming.ondernemersaftrek_totaal`,
`onderneming.mkb_winstvrijstelling`, or
`onderneming.kleinschaligheidsinvesteringsaftrek`. Manual-entry rows cover only
what the taxpayer actually types, and every `onderneming.*` row stays conditional
or optional. Print each double-entry fact once in the workpack and twice in the
manual-entry checklist, one line per screen path.

### Vermogensvergelijking self-check

The section MUST carry the reconciliation as an explicit self-check line: the
Winstberekening screen reproduces the profit from the movement in the
ondernemingsvermogen, and for an eenmanszaak it must agree with the saldo
winst-en-verliesrekening. Ask for the opening and the closing
ondernemingsvermogen as two separate figures; never carry a prior year's closing
column forward and never enter zero for a column the taxpayer did not supply. Do
not invent the signed formula and do not encode a balance tolerance. Report a
mismatch with the components it rests on and route it to manual review; never
adjust a figure to force agreement.

### Bijdrage Zvw

An ondernemer receives a **second, separate aanslag** for the
inkomensafhankelijke bijdrage Zorgverzekeringswet, alongside the aanslag
inkomstenbelasting, and the return the taxpayer files covers both. The section
MUST say so, name the belastbare winst uit onderneming as the bijdrage-inkomen
component, and take the percentage, the maximumbijdrage-inkomen, the interaction
with loon, and the resultaat-uit-overige-werkzaamheden treatment from
`../nl-tax-shared-resources/knowledge/years/2025/entrepreneur/zvw-2025.md`. The bijdrage is never a
business cost and never re-enters the profit chain in either direction.

### Loss outcome

A negative belastbare winst uit onderneming is an ondernemingsverlies. State
that the MKB-winstvrijstelling made the loss smaller, that the loss is first set
off within 2025 against positive box 1 income such as loon, and that a loss year
still requires a filed return. Take the carry-back and carry-forward windows,
the beschikking, and the niet-gerealiseerde zelfstandigenaftrek settlement from
`../nl-tax-shared-resources/knowledge/years/2025/entrepreneur/verlies-en-verrekening-2025.md`; do
not restate them here.

### Field-map readiness for a business case

The annual field map reaches `readiness: review_ready` when the reviewed
zakelijke schema covers every business rubriek and question the case needs and
no manual-review routing marker below applies. It stays `readiness: draft` with
the manual-review blocker `business-section schema review` when a needed
rubriek, question, or identifier is outside the reviewed zakelijke schema, or
when any routing marker applies. Readiness is otherwise derived from the same
annual section-status rollup as the STATUS banner.

"Covers every" requires an explicit per-identifier audit across the complete
W&V, balance, private-movement, prior-year-set-off and entrepreneur-question
inventories. Each identifier is mapped, sourced as not applicable, or unresolved;
an omitted row or unanswered question is unresolved and keeps the map draft.
`business.legal_form` and `onderneming.routing.complex_case` are sourced internal
routing records and never appear in the taxpayer's portal-entry checklist. The
optional validator cannot replace or relax this audit.

### Winst uit onderneming manual-review routing

Recognising a business form is no longer terminal. Name the form, state what it
does to the ondernemer tests, and continue preparing the parts of the return it
does not block, using
`../nl-tax-shared-resources/knowledge/years/2025/entrepreneur/samenwerkingsverband-2025.md` and
`../nl-tax-shared-resources/knowledge/years/2025/entrepreneur/staking-2025.md` for the recognition
and routing. What stays terminal is the **computation**. The workpack MUST route
to manual review, without producing a partial calculation, for:

- the **profit-share computation** of a samenwerkingsverband (vof, maatschap,
  man-vrouwfirma, cv) -- the winstaandeel, the KIA apportionment, and the
  per-participant figures;
- the **loss caps** applying to a medegerechtigde or a profit-sharing
  geldverstrekker;
- **DGA or BV winst**;
- **agrarische ondernemingen** (landbouwvrijstelling);
- **zeevarenden** (zeescheepvaart);
- the **stakingswinst computation**, doorschuiving, and the stakingslijfrente;
- any **herinvesteringsreserve** movement;
- the **oudedagsreserve wind-down computation**;
- **terbeschikkingstelling** of assets to a connected company or enterprise.

For each marker, record the collected facts, name the figure that could not be
computed and why, and hand the case to professional review.

Resultaat uit overige werkzaamheden is **not** on that list. It is a prepared
path: when the income-category screen in
`../nl-tax-shared-resources/knowledge/years/2025/entrepreneur/row-en-dba-2025.md` places the
activity outside winst uit onderneming and outside dienstbetrekking, prepare the
ROW result in the Income notes section under that note, still emitting the
canonical `business.has_onderneming: no` hook here. Ondernemersaftrek,
MKB-winstvrijstelling and investeringsaftrek are ondernemer facilities and never
apply to a ROW result.

## Box 2 requirements

### Standard Box 2 preparation

The Box 2 section MUST be present.

**When Box 2 does not apply** (no aanmerkelijk belang and no Box 2 facts in the case), emit exactly:

```
Not applicable — no substantial interest (aanmerkelijk belang) reported.
box2.has_aanmerkelijk_belang: no
```

Do not enumerate the other 10 fields. The single `box2.has_aanmerkelijk_belang: no` line is the canonical hook for the field map.

**When Box 2 applies**, include standard preparation fields for:

- `box2.has_aanmerkelijk_belang`
- `box2.reguliere_voordelen_bruto`
- `box2.kosten_reguliere_voordelen`
- `box2.vervreemdingsprijs`
- `box2.verkrijgingsprijs`
- `box2.vervreemdingskosten`
- `box2.vervreemdingsvoordeel`
- `box2.fictief_regulier_voordeel_bv_lening`
- `box2.ingehouden_dividendbelasting`
- `box2.te_verrekenen_verlies_ab`
- `partner.verdeling_box2_inkomen`

Regular benefits include dividends. Disposal benefits include share-sale profit; the standard preparation formula is official net transfer price minus acquisition price. If evidence starts from gross sale proceeds, subtract disposal costs once to derive the net transfer price first. Dividend withholding tax may be credited when supported by evidence.

### Box 2 manual-review routing

The workpack MUST route Box 2 to manual review or unsupported when facts involve valuation disputes, emigration, death, restructurings, treaty/nonresident issues, informal capital, non-arm's-length transfers, or corporate-tax-heavy DGA issues.

If fiscal partners allocate Box 2 income, the workpack MUST show the allocation percentage and verify that the total allocation equals 100%. Do not present allocation as final filing advice.

## Box 3 requirements

### Both methods explained; actual-return inputs optional

The box 3 section MUST include notes for BOTH methods:

1. **Fictitious return (forfaitair rendement):** Full calculation with asset categories, percentages, aftrekbare schulden, belastbaar rendement, rendementsgrondslag, grondslag sparen en beleggen, aandeel in rendementsgrondslag, box 3 income, and tax amount. Use the rates from `../nl-tax-shared-resources/knowledge/years/2025/box3/fictitious.md` — never paraphrase from memory.
2. **Actual return (werkelijk rendement) data collection:** Data gathered or gaps identified for interest, dividends, rental income, capital gains/losses, unrealized value changes, interest paid on box 3 debts, and qualifying WOZ-value investment correction.

If all required actual-return inputs are available, file and chat provenance are
equally valid for completeness. Record the `box3_actual` section as `complete` when the
inputs include document evidence, or `chat_only` when the complete input set was
stated in chat. Cross-index every chat value for human review. An explicit
decision not to provide actual return is also complete: record `not supplied by
choice`, prepare the fictitious-return workpack, and do not create a Missing
information item. Only required facts still missing after the taxpayer chose the comparison
may make the section `deferred/manual review`; list those inputs and do not
imply that both calculations were completed.

### Comparison section

When actual-return inputs were supplied, the comparison subsection must present
both figures and note which is more favorable. When the taxpayer declined, it
must instead say that no actual-return comparison was prepared by choice. In
both cases, explain that the official filing environment performs the binding
calculation and selection.

### Partner allocation

If fiscal partners are present, the box 3 section must include:
- At least two labeled, traceable comparison scenarios (for example, 50/50 and
  one materially different eligible split), without calling either scenario a
  default, recommendation, optimum, or best result
- Each scenario's percentages, estimated individual and combined effects,
  difference versus Scenario A, assumptions, uncertainty, and provenance
- `Taxpayer-selected allocation: [not selected / user-confirmed split]` with
  `U:` provenance; leave it unresolved until the taxpayer explicitly chooses
- A note that any taxpayer-selected percentage applies to the entire box 3 base

The workpack must not rank, recommend, or automatically select an allocation.
It supplies comparison scenarios; the taxpayers review them and make the
choice themselves in the official filing environment.

## Credits screening requirements

The Credits screening section MUST list `candidate`, `not applicable`, or
`unresolved` for each credit below. Profile data starts the questions; it does
not determine the outcome by itself:

- **IACK (inkomensafhankelijke combinatiekorting)** — record child age,
  including whether the child was **younger than 12 on 1 January 2025**,
  6-month household status or exact co-parent day/rhythm facts, the child-death
  exception when relevant, arbeidsinkomen above EUR 6,145, fiscal-partner
  duration, both partners' arbeidsinkomen, and the older partner for equal
  incomes. Missing facts make the result `unresolved`, not `not applicable`.
- **Ouderenkorting** — candidate when the taxpayer has reached AOW age by
  31 December 2025; verify the amount in the official return.
- **Alleenstaande-ouderenkorting** — triggered only when the taxpayer is entitled
  to an AOW benefit for a single person; ask for the AOW entitlement and do not
  infer it from household or fiscal-partner fields.
- **Jonggehandicaptenkorting** — triggered only when the taxpayer receives or is
  entitled to a Wajong-uitkering / Wajong work support and does not receive the
  ouderenkorting. A reported young-disabled status counts only when it establishes
  that Wajong entitlement or work support. Ask the dedicated yes/no question
  `annual.credits.young_disabled_status`; do not infer the answer from age or a
  broad denial of other benefits, deductions, or credits.
- **Possible payout of unused algemene heffingskorting** — when low/no income
  leaves an apparently unused credit, screen own unused credit, being born before
  1963, more than 6 months with the same fiscal partner (with the partner-death
  exception), and sufficient Dutch tax/premium liability of that partner after
  the partner's own credits. Do not assume the EUR 3,068 maximum is payable.

For each candidate credit, list the answered conditions and instruct the user
to verify the calculated amount in Mijn Belastingdienst. Keep unanswered
conditions visible; do not force an eligibility result.

For each credit that did **not** trigger, emit one line: "Not applicable — [reason in one phrase]". Do not collapse the section to a single "no credits" line; the taxpayer needs to see each trigger was considered.

## Field map requirements

### Separate from provisional

The canonical field map for this workpack is the fenced `yaml` block in
Appendix B, with `workflow: annual_return`; `Field map summary` is its
human-readable table. `nl-tax-field-mapper` is the only author of both. The
mapper shows the summary table in the conversation; the YAML is composed and
checked but never printed in chat, and is written only into a saved workpack.

Do NOT reference, reuse, or link to a provisional field map or the provisional
workpack. The annual and provisional field maps are entirely separate.

### Content requirements

The field map must map each major workpack line item to:

## Status banner

Every workpack MUST open with a STATUS banner that the owning agent reconciles
with the annual section-status rollup it tracks in the conversation and, when
the workpack is saved, in Appendix A. This is a consistency and resumability
check, not an independent workflow or tax-decision engine. Use the rollup of
the annual sections:

- If any applicable section is `deferred` or has `unknown`/open blocking items, the banner reads: `STATUS: DRAFT — N deferred section(s)` where `N` is the count of deferred/incomplete sections.
- If every applicable section is `complete` or `chat_only`, the banner reads: `STATUS: COMPLETE DRAFT FOR REVIEW`.

In both cases the banner MUST also state that the workpack is **not for filing** (e.g. append "not for filing — review and submit manually via Mijn Belastingdienst"). Reconcile the banner with the section statuses on every assembly so the two do not drift.

The Appendix B field map MUST carry a matching **top-level** `readiness` field,
and Appendix A `readiness` MUST carry the same value: `draft` when this banner
is `DRAFT`, and `review_ready` when this banner is `COMPLETE DRAFT FOR REVIEW`,
unless a workflow-specific blocker (such as business schema review) requires
`draft`. The agent derives all three from the same rollup. An optional
validator may reject an impossible `review_ready` declaration but never promote
`draft`.

  `credits_screening`, `partner_allocation`, and `confirm`, each as
  `{status: <not_started | in_progress | complete | chat_only | deferred>, open: [<Q-IDs>]}`.
- `save_consent` defaults to `not_given` in the template and becomes `given` in
  the written file (saved in the working folder or delivered as a download).
  It is a record, never an authorization: a writer checks that save consent is

- `queued_workflow` is `null`, or the queued 2026 subflow value when the
  taxpayer asked for both workflows.
- Facts never live in the resume record; they live in the readable sections
  with provenance.
